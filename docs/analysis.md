## 3. 硬件依赖与不可从手册直接确定的事项

- **强制 DI**：507=0x01FB、511=0x01FF，依据 DI3 默认低有效 S-ON。P0D-17 强制 DI 后物理 DI4/DI5 是否仍保护、P0B-03 是物理还是强制值，手册不足以确定。不能声称硬限位已失效，也不能假定它有效。需要厂家答复及独立硬急停下的受控验证。
- **EEPROM**：P0C-13 出厂 1，频繁写 P10 会更新 EEPROM；手册要求设为 0。原程序未检查，现场是否已设正确未知。
- **单位/字序**：P0C-26 可改字序；P05-02 与电子齿轮参数决定每转指令数。10000 与 0.35cm/转是当前配置/现场基线，不是所有驱动器固有常量。
- **制动**：用户已确认电机无抱闸、传动系统自锁。原停后5秒断使能与急停立即断使能仍需验证自锁承载和瞬态位移；不能只修改软件延时宣称解决动态停止。
- **减速度**：P10-27/29/31 决定加减速/急停；程序没有读取确认。发出 256/512 不意味着电机瞬时静止。
- **B00**：手册还列出堵转、接线和转矩不足等原因。对齐 P10-14 不能证明内部位置误差或机械故障消失；不宜隐式自动复位。
- **通信失联**：PC 端软件无法在网线断开时保证停止命令到达。必须通过驱动器/外部硬件联锁验证失联策略；模拟结果仅用于验证软件行为。

## 4. 架构问题

1. `main.py` 同时承担参数模型、文件持久化、全局状态、驱动适配、保护逻辑、租约和 HTTP。升降功能依赖全局 `settings/lift_state`；无法给第二台设备创建独立实例，测试间也易污染。应以一个控制器拥有一个配置、状态和驱动实例。
2. 停止/急停/异常/报警/超时多处重复清理 `_pv_*`、stall、target 字段。已有 `_clear_jog_runtime` 仍未统一使用，差异造成 F01/F02。应统一状态转换，而不是把所有异常共用“清空状态”函数。
3. `command_goto` 与 `command_position_bound` 重复；PP/PV 准备、使能和异常处理重复；速度 PP/PV 换算重复。可提取目标构造、限幅、准备/启动步骤，但停止和急停不能为了复用丢掉不同语义。
4. Settings 与 ConfigUpdate 两套字段、env 映射、to_dict、to_settings 重复；新增参数容易漏传。应统一配置 schema，标定/运行状态与可编辑参数分开存储。
5. 本地 HTTP 与 Bridge 各自判断租约/操作权限；前端也把急停当普通命令。应统一策略层，入口只给出可信来源和操作者；角色应依据经过验证的身份确定。
6. 模拟路径与真实路径完全分叉，导致模拟“通过”没有覆盖报文和真实时序。调试工具应在协议/传输边界模拟，同一控制器跑模拟和实机。
7. 前端车顶面板/升降抽屉复制控件绑定和目标/速度换算；前后端各硬编码 10000、0.35。应复用一个控件组件，换算以服务端配置为准。
8. 事务锁只保证单帧串行，不能保护整个状态转换；HTTP 锁又令急停等待完整启动。应单设备顺序执行，停止意图独立登记，每个有限时长步骤后检查代次。
9. 通信失败不等于停止；`online`、`motion`、`position_trusted` 不应互相替代。状态应含观测时间、请求/执行目标、未知运动、停机待确认与故障锁存。
10. `TsdaLiftClient` 历史别名、废弃步进字段、不同文档配置入口不一致扩大维护成本。新工具不把旧 TSDA 接口作为新领域模型。

## 5. 修改原则

先建立功能对应与失败复现，再在独立工具中验证候选状态机。原行为保留为**仅模拟的冻结基线**；功能等价不等于继续保留缺陷。候选实现的行为差异必须明示。完成离线、假驱动网络测试后，再由现场确认 DI/抱闸/计数条件，进行低速、小位移受控试验。本审查不修改原项目。
